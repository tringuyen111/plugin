# Projection Contract

Use this reference when a System Plane law must appear in resident Plugin context, a standalone Skill, an evaluation, or another consumer.

## Projection classes

### Resident

Keep only semantics that must remain salient across ordinary work and context transitions. Resident projection is a decision-dense reminder, not a copy of the complete plane and not a lifecycle router.

### Skill-local

A first-class Skill must retain enough local governing semantics to perform its accountable job independently. Compact repetition is valid when removing it would weaken standalone correctness.

Never replace required local reasoning with a conditional System Plane reference load or another sibling dependency.

### Evaluation

Qualification cases name the law/invariant they can falsify and bind to exact candidate revision. Tests may duplicate a rule as an assertion; they are evidence consumers, not semantic authority.

### Runtime/orchestration mechanism

State stores, working ledgers, paging/rehydration, active-owner control, and capability activation can implement System Plane laws. They do not become System Plane semantics merely because they are shared infrastructure.

## Projection rules

1. **Project meaning, not wording.** Domain language may differ while preserving the semantic relation.
2. **Use the smallest sufficient surface.** A projection must earn its context cost; do not copy the whole plane "for safety".
3. **Keep authority direction intact.** Projection must not grant user-owned decisions to an agent or supporting Skill.
4. **Keep evidence boundaries intact.** `FAIL`, `NOT_RUN`, `MISSING`, `BLOCKED`, and claim-local blockers must survive compression.
5. **Preserve re-entry scope.** If evidence invalidates an earlier premise, local workflow must reopen every material dependent decision/claim while preserving independent proven state; a shared/root premise may invalidate the whole local outcome.
6. **Avoid hidden runtime dependency.** Ordinary work must not require the conditional System Plane method to be loaded merely to access a governing law.
7. **Avoid route creation.** Projection does not imply a next/previous Skill or fixed SDLC phase graph.

## Semantic equivalence check

A projection is faithful only when compression/localization preserves all decision-material parts of the law:

- applicability / trigger;
- normative direction (`must`, `may`, `must not`);
- authority and accountable owner;
- state/evidence distinctions;
- scope and boundary;
- consequence, stop condition, dependency reach, and re-entry/invalidation scope.

Use at least one counterexample when drift would be costly: the canonical law and the projection should produce the same bounded decision on that case. If one of these dimensions changes, treat the projection as a semantic revision or faulty projection rather than "equivalent wording".

## Projection gate

For each changed law ask, in order:

1. Which consumer can become incorrect if it does not carry this meaning?
2. Is the meaning required continuously (`resident`) or only inside one accountable job (`Skill-local`)?
3. Is the consumer actually a mechanism rather than a semantic projection?
4. Can a smaller expression preserve the law without losing authority, evidence state, or dependency-scoped re-entry?
5. Which evaluation must change because its assertion meaning changed?

Update only material consumers. Similar wording is not dependency evidence.
