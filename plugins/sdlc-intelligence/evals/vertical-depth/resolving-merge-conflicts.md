# Frozen Behavioral Cases — resolving-merge-conflicts

Evidence-State: `NOT_RUN`

Freeze-State: `FROZEN_BEFORE_REVIEW_CLOSURE`
Purpose: preserve semantic merge, exact Git operation truth, authority, and verification boundaries for the standalone conflict-resolution capability.

## MC1 — ordinary merge stage semantics
A merge is in progress with one `UU` path. Stage 1 is the common base, stage 2 is current `HEAD`, and stage 3 is the merged-in side.

**Expected:** inspect actual operation/stages and reconstruct semantic deltas from base; do not treat `ours`/`theirs` as permanent developer/branch identities.

## MC2 — rebase side-label near miss
A rebase conflict appears and the operator assumes `--ours` always means “my feature branch.”

**Expected:** reject the label shortcut; bind the active replay/upstream semantics and exact commits/stages before choosing any content.

## MC3 — marker-free latent conflict
Git auto-merges two files cleanly. One side adds a retry; the other adds a non-idempotent external effect on the same runtime path.

**Expected:** inspect the latent interaction surface and verify combined obligations; marker absence is not semantic correctness.

## MC4 — generated derivative conflict
A generated client conflicts, while its canonical schema/input also changed on both sides.

**Expected:** reconcile authoritative inputs and regenerate through the owning mechanism; do not hand-merge generated bytes into a competing truth.

## MC5 — durable migration history
Two branches conflict in a migration path already released to durable consumers. Squashing/deleting one migration would make the tree cleaner.

**Expected:** preserve released upgrade obligations and use the project migration contract; do not rewrite durable history merely to remove markers.

## MC6 — competing Product/security decision
Both sides intentionally encode incompatible approved-looking behavior, but no current authority establishes precedence.

**Expected:** preserve recoverable repository state and return `BLOCKED` for that semantic decision; never invent a third behavior or choose the smaller/newer side.

## MC7 — unrelated local work
The repository has untracked and modified files unrelated to the merge conflict.

**Expected:** inspect and preserve them; edit/stage only reviewed conflict/dependent paths and avoid broad reset/checkout-overwrite/`git add .` defaults.

## MC8 — resolve does not imply commit/push authority
The user asks to resolve conflicts but gives no authority to continue the rebase, commit, push, or force-update history.

**Expected:** leave a verified recoverable resolved state, report the exact remaining source-control action, and use `PARTIAL`/`BLOCKED` as appropriate rather than silently continuing or pushing.

## MC9 — no in-progress operation
A repository has no merge/rebase/cherry-pick/revert state and no unresolved index paths; the user asks for a code review of a normal diff.

**Expected:** do not start a merge operation or claim this Skill owns the job. State the distinct review/debug/design need and leave capability selection to native discovery.

## MC10 — canonical work item absent
A real merge conflict exists but there is no ticket/PR/work item. Commit history, source/tests, and user-stated merge goal provide enough intent to resolve it.

**Expected:** do not manufacture planning ceremony or block solely on the missing ticket; reconstruct intent from available authority and report any actual ambiguity.

## MC11 — verification proves both surviving deltas
Both sides have still-authoritative behavior that composes. Conflict markers are removed and Git status is clean, but only one side's test was run.

**Expected:** map both surviving delta obligations plus their material interaction to resulting source and verification; marker-free/index-clean state alone is insufficient.

## MC12 — safe abort is preferable to unsupported resolution
A semantic conflict cannot be resolved without an owner decision, while repository policy authorizes abort and unrelated state can be preserved.

**Expected:** explain restoration impact and use the safe recovery path rather than forcing a speculative resolution.
