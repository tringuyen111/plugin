# Frozen Qualification — Capability Activation / Composition F6b

Evidence-State: `NOT_RUN`


Maintenance-only cases for F6 capability activation/composition. Native metadata checks, hook JSON execution, and package validation are structural/mechanics proof only; they do not establish model activation recall/precision or composition behavior.

## 1. Unknown cause selects diagnosis depth, not speculative implementation
- Situation: production bug exists; material root cause is unknown.
- Expected: express a causal-diagnosis capability need and use diagnosing depth when useful; do not activate Implement merely because code may eventually change.
- Falsifier: speculative mutation starts from a guessed cause or a fixed phase route.

## 2. Proven cause does not force diagnosis ceremony
- Situation: root cause is already proven and correction is authorized.
- Expected: use implementation/relevant specialist depth directly when it can change the correction or proof.
- Falsifier: require Diagnosis only because it precedes Implement in an imagined lifecycle.

## 3. Broad checkout change composes bounded specialist depth
- Situation: one checkout/payment change materially touches frontend, API, backend, durable data, and security semantics.
- Expected: share one bound truth packet; activate only decision-changing specialist depth; reconcile/fan in before shared mutation; keep one live Outcome.
- Falsifier: create Skill workers/owners, let each redefine the feature independently, or mutate shared seams before reconciling conflicting assumptions.

## 4. Immutable review remains review
- Situation: user asks for review of a frozen PR/change.
- Expected: Code Review owns the review job; domain depth may inform findings but does not turn into mutation workers.
- Falsifier: auto-route into implementation because engineering Skills are available.

## 5. Provider / Source Selection remains provider/source resolution
- Situation: required capability is known, but provider/source is ambiguous.
- Expected: Provider / Source Selection may choose the provider/source for that capability.
- Falsifier: use Provider / Source Selection to choose the Skill/job or route SDLC phases.

## 6. Discoverable specialist still enforces its own entry gate
- Situation: user asks to challenge a material decision and native metadata allows Decision Interview automatic discovery.
- Expected: native discovery may expose Decision Interview, but the Skill still binds a concrete decision surface, uses its zero-question path when no material human frontier exists, and never gains protected decision/write authority merely because it was selected.
- Falsifier: require explicit invocation despite discoverable metadata, treat selection as authority to manufacture an interview, or add Plugin-side ranking/recovery to force activation.

## 7. Native discovery remains authoritative
- Situation: native discovery omits or misses a materially fitting installed Skill.
- Expected: continue with base competence when sufficient, allow explicit invocation when requested, and refine native Skill name/description/policy if repeated evidence shows a discovery defect.
- Falsifier: consult or build a Plugin-maintained candidate ranker, route/index, or active-Skill state to compensate at runtime.

## 8. Missing Skill is not automatically BLOCKED
- Situation: a useful named Skill is unavailable.
- Expected: continue with base competence when the bounded decision/proof remains supportable; keep only the real missing expertise/tool/context obligation open.
- Falsifier: declare the whole outcome blocked merely because a sibling Skill name is absent.

## 9. Same-dimension conflict is typed, not voted
- Situation: two activated capabilities disagree on the same material semantic dimension.
- Expected: preserve contradiction/provenance and resolve by actual authority, current evidence, capability scope, and governing constraints; block/reopen only dependent state if unresolved.
- Falsifier: choose by load order, recency, verbosity, or majority vote.

## 10. Second Skill does not reset F2
- Situation: another capability becomes useful mid-task.
- Expected: preserve Outcome and bound truth; ask a bounded capability question; integrate its result; update affected obligations/frontier only.
- Falsifier: reset the task or narrate a same-Agent handoff/ownership transfer.

## 11. Real transfer still uses Handoff
- Situation: work actually crosses agent/session/runtime/authority boundary and state must transfer.
- Expected: use real handoff semantics; receiving Agent re-binds its own control state.
- Falsifier: equate ordinary Skill activation with handoff or skip required transfer state at a real boundary.

## 12. Broad SDLC request remains frontier-driven
- Situation: user asks broadly for SDLC help.
- Expected: SDLC may judge which lifecycle concerns are material, while capability depth is selected from the current frontier rather than a fixed Product -> Requirements -> Design -> Engineering -> QA chain.
- Falsifier: execute a ceremonial phase route independent of current truth/materiality.

## 13. Capability composition remains provider-portable
- Situation: one Skill needs bounded depth or evidence owned by another installed capability.
- Expected: name the capability/need and let native discovery or explicit user invocation resolve it; project artifacts and reusable Skill context do not require host-specific `/skill-name` command syntax.
- Falsifier: active Skill guidance encodes sibling capability selection as a slash command or treats slash syntax as the portable composition contract.
